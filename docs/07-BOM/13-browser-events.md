# Browser Events

Browser events are notifications generated by the browser when something happens in the web page, document, window, or user interface.

Examples include:

* A user clicks a button
* The keyboard receives input
* The pointer moves
* The page loads
* The browser window resizes
* The user scrolls
* The page becomes visible or hidden
* The browser starts or finishes navigation-related activity
* The network state changes
* The user leaves or enters the page

JavaScript can listen for these events and execute callback functions in response.

The fundamental pattern is:

```js
target.addEventListener("event", handler);
```

For example:

```js
window.addEventListener("resize", () => {
  console.log("Window resized.");
});
```

Browser events are one of the most important concepts in web development because they connect JavaScript code to activity happening in the browser.

---

# 1. What Is an Event?

An event is a notification that something happened.

For example:

```text
User clicks a button
        ↓
Browser creates a click event
        ↓
Registered event handler runs
```

Another example:

```text
Window changes size
        ↓
Browser dispatches resize event
        ↓
Registered callback runs
```

Events are asynchronous from the perspective of application logic: something happens in the environment, and the browser later invokes the corresponding handler.

---

# 2. Event-Driven Programming

Web applications are largely event-driven.

Instead of continuously asking:

```js
"Did the user click?"
"Did the user click?"
"Did the user click?"
```

JavaScript registers interest in the event:

```js
button.addEventListener("click", handleClick);
```

The browser notifies the application when the event occurs.

This is more efficient and matches the browser's programming model.

---

# 3. `addEventListener()`

The standard way to listen for browser events is:

```js
target.addEventListener(type, listener);
```

Example:

```js
const button = document.querySelector("#save");

button.addEventListener("click", () => {
  console.log("Save button clicked.");
});
```

The main pieces are:

```text
target
  ↓
Object receiving the event

event type
  ↓
"click"

listener
  ↓
Function executed when the event occurs
```

---

# 4. The Event Target

Events can be associated with many different objects.

Examples:

```js
window.addEventListener("resize", handler);
document.addEventListener("keydown", handler);
button.addEventListener("click", handler);
input.addEventListener("input", handler);
```

The target can be:

* `window`
* `document`
* an HTML element
* other browser objects that support events

---

# 5. Event Types

An event type is usually represented by a string.

Examples:

```js
"click"
"keydown"
"input"
"submit"
"load"
"resize"
"scroll"
"focus"
"blur"
"online"
"offline"
"visibilitychange"
```

Example:

```js
window.addEventListener("online", () => {
  console.log("Browser reports an online state.");
});
```

The event name must match the API's expected event type.

---

# 6. Event Handlers

The function registered to respond to an event is called an event handler or listener.

Example:

```js
function handleClick() {
  console.log("Button clicked.");
}

button.addEventListener("click", handleClick);
```

You can also use an inline arrow function:

```js
button.addEventListener("click", () => {
  console.log("Button clicked.");
});
```

Both approaches are valid.

---

# 7. Why Named Handlers Can Be Useful

A named function is especially useful when you need to remove the listener later.

```js
function handleResize() {
  console.log(window.innerWidth);
}

window.addEventListener("resize", handleResize);
```

Later:

```js
window.removeEventListener("resize", handleResize);
```

If the callback is written as an anonymous function, you do not have the same function reference available for removal:

```js
window.addEventListener("resize", () => {
  console.log(window.innerWidth);
});
```

This is why reusable handlers are often preferable when cleanup is required.

---

# 8. `removeEventListener()`

Use:

```js
target.removeEventListener(type, listener);
```

Example:

```js
function handleResize() {
  console.log("Resized.");
}

window.addEventListener("resize", handleResize);

window.removeEventListener("resize", handleResize);
```

The function reference matters.

This works:

```js
window.removeEventListener("resize", handleResize);
```

This does not remove the original listener:

```js
window.removeEventListener("resize", () => {
  console.log("Resized.");
});
```

The two arrow functions are different function objects.

---

# 9. Why Event Cleanup Matters

Unremoved event listeners can cause:

* unnecessary work
* duplicate callbacks
* memory retention
* stale state access
* unexpected behavior

This becomes especially important in:

* React components
* single-page applications
* reusable widgets
* long-lived pages

---

# 10. The Event Object

When an event occurs, the browser creates an event object containing information about that event.

Example:

```js
button.addEventListener("click", (event) => {
  console.log(event);
});
```

The event object can contain information such as:

* event type
* target
* current target
* keyboard information
* pointer coordinates
* modifier keys
* propagation state
* timestamp-related information

The exact properties depend on the event type.

---

# 11. `event.type`

`event.type` contains the event type.

```js
button.addEventListener("click", (event) => {
  console.log(event.type);
});
```

Output:

```text
click
```

This can be useful in generic event handlers.

---

# 12. `event.target`

`event.target` identifies the object on which the event originated.

Example:

```js
button.addEventListener("click", (event) => {
  console.log(event.target);
});
```

For a button click, this is usually the button element.

However, in event delegation, `target` can be different from the element that owns the listener.

---

# 13. `event.currentTarget`

`event.currentTarget` identifies the object whose listener is currently executing.

Example:

```js
button.addEventListener("click", (event) => {
  console.log(event.target);
  console.log(event.currentTarget);
});
```

For a direct listener, they may be the same.

In bubbling scenarios they can differ.

This distinction is critical for event delegation.

---

# 14. `target` vs `currentTarget`

Consider:

```html
<div id="container">
  <button id="save">
    <span>Save</span>
  </button>
</div>
```

Suppose the listener is on the button:

```js
const button = document.querySelector("#save");

button.addEventListener("click", (event) => {
  console.log(event.target);
  console.log(event.currentTarget);
});
```

If the user clicks the `<span>`, then conceptually:

```text
event.target
↓
<span>

event.currentTarget
↓
<button>
```

This difference is extremely important when working with nested elements.

---

# 15. Event Propagation

Browser events can move through the DOM.

The main propagation phases are:

```text
Capture phase
      ↓
Target phase
      ↓
Bubble phase
```

This allows an event originating from a deeply nested element to be observed by ancestors.

---

# 16. Event Bubbling

Most commonly used browser events bubble.

Example:

```html
<div id="container">
  <button id="save">
    Save
  </button>
</div>
```

Listeners:

```js
const container = document.querySelector("#container");
const button = document.querySelector("#save");

container.addEventListener("click", () => {
  console.log("Container");
});

button.addEventListener("click", () => {
  console.log("Button");
});
```

Clicking the button can produce:

```text
Button
Container
```

The event starts at the target and then bubbles upward.

---

# 17. Stopping Propagation

You can stop an event from continuing through the propagation path:

```js
button.addEventListener("click", (event) => {
  event.stopPropagation();
});
```

This is powerful but should not be used casually.

Stopping propagation can interfere with:

* parent components
* event delegation
* accessibility-related behavior
* application-level event handling

Use it when the propagation behavior is genuinely unwanted.

---

# 18. `preventDefault()`

`preventDefault()` is different from `stopPropagation()`.

`preventDefault()` prevents the browser's default action associated with the event.

Example:

```js
const link = document.querySelector("#profile");

link.addEventListener("click", (event) => {
  event.preventDefault();

  console.log("Navigation prevented.");
});
```

The event can still propagate unless propagation is also stopped.

---

# 19. `preventDefault()` vs `stopPropagation()`

| Method                       | Purpose                                                                      |
| ---------------------------- | ---------------------------------------------------------------------------- |
| `preventDefault()`           | Prevent the browser's default action                                         |
| `stopPropagation()`          | Stop event propagation                                                       |
| `stopImmediatePropagation()` | Stop propagation and prevent other listeners on the same target from running |

These solve different problems.

---

# 20. Example: Form Submission

A form normally submits when the user presses its submit button.

You can intercept it:

```js
const form = document.querySelector("#contact-form");

form.addEventListener("submit", (event) => {
  event.preventDefault();

  console.log("Custom submission logic.");
});
```

The browser's default navigation is prevented.

This pattern is fundamental to client-side applications.

---

# 21. Event Capturing

Listeners normally run during the bubbling phase.

You can explicitly listen during the capture phase:

```js
container.addEventListener(
  "click",
  handleClick,
  true
);
```

Or using an options object:

```js
container.addEventListener(
  "click",
  handleClick,
  { capture: true }
);
```

The capture phase moves from ancestors toward the target.

---

# 22. Propagation Order

Conceptually:

```text
window
  ↓
document
  ↓
html
  ↓
body
  ↓
parent
  ↓
target
  ↑
parent
  ↑
body
  ↑
html
  ↑
document
  ↑
window
```

The downward direction represents capture.

The upward direction represents bubbling.

Not every event behaves identically, so always consider the specific event type.

---

# 23. Event Listener Options

`addEventListener()` can receive an options object.

Example:

```js
element.addEventListener(
  "click",
  handleClick,
  {
    once: true,
    capture: false,
  }
);
```

Common options include:

* `capture`
* `once`
* `passive`
* `signal`

These options change listener behavior.

---

# 24. The `once` Option

`once: true` automatically removes the listener after its first invocation.

```js
button.addEventListener(
  "click",
  () => {
    console.log("This runs once.");
  },
  { once: true }
);
```

After the first click, the listener is removed.

This is useful when an action should happen only once.

---

# 25. The `passive` Option

A passive listener tells the browser that the handler will not call `preventDefault()`.

Example:

```js
window.addEventListener(
  "touchmove",
  handleTouchMove,
  { passive: true }
);
```

This can help the browser optimize certain input and scrolling interactions.

Do not mark a listener as passive if the handler needs to cancel the default action with:

```js
event.preventDefault();
```

---

# 26. The `signal` Option

An `AbortController` can control event listener lifetime.

Example:

```js
const controller = new AbortController();

window.addEventListener(
  "resize",
  handleResize,
  {
    signal: controller.signal,
  }
);
```

Later:

```js
controller.abort();
```

The browser removes listeners associated with that signal.

This can be convenient when managing multiple listeners as one lifecycle unit.

---

# 27. Multiple Listeners

Multiple listeners can be attached to the same target and event type.

```js
button.addEventListener("click", handleSave);
button.addEventListener("click", handleAnalytics);
```

Both can run when the event occurs.

This is useful when separate parts of an application need to react to the same event.

However, excessive event listeners can make behavior harder to reason about.

---

# 28. `stopImmediatePropagation()`

If multiple listeners are registered on the same target, `stopPropagation()` does not necessarily stop the other listeners on that same target.

`stopImmediatePropagation()` is stronger:

```js
button.addEventListener("click", (event) => {
  event.stopImmediatePropagation();
});
```

It prevents further listeners for that event from running on the current target and stops further propagation.

Use this carefully because it can interfere with unrelated behavior.

---

# 29. Mouse Events

Traditional mouse events include:

```text
click
dblclick
mousedown
mouseup
mousemove
mouseenter
mouseleave
mouseover
mouseout
```

Example:

```js
button.addEventListener("click", () => {
  console.log("Clicked.");
});
```

For modern pointer-aware interfaces, Pointer Events are often a better abstraction.

---

# 30. `mouseenter` vs `mouseover`

These events are related but behave differently.

`mouseenter` generally does not bubble.

`mouseover` bubbles and can fire when moving between child elements.

Example:

```js
element.addEventListener("mouseenter", handleEnter);
element.addEventListener("mouseleave", handleLeave);
```

These are often convenient for simple hover behavior.

---

# 31. Pointer Events

Pointer Events provide a unified model for various pointing devices.

Common events include:

```text
pointerdown
pointerup
pointermove
pointerenter
pointerleave
pointercancel
```

A pointer can represent:

* mouse
* touch
* pen/stylus

Example:

```js
button.addEventListener("pointerdown", (event) => {
  console.log(event.pointerType);
});
```

Possible values include:

```text
mouse
touch
pen
```

This can simplify cross-device interaction handling.

---

# 32. Pointer Events vs Mouse Events

Instead of writing separate interaction systems for:

```text
mouse
touch
pen
```

Pointer Events provide one general event model.

For modern interactive components, Pointer Events are often worth understanding.

---

# 33. Keyboard Events

Important keyboard events include:

```text
keydown
keyup
```

Example:

```js
document.addEventListener("keydown", (event) => {
  console.log(event.key);
});
```

If the user presses Enter:

```text
Enter
```

may be reported as:

```js
event.key === "Enter"
```

---

# 34. `keydown` vs `keyup`

`keydown` occurs when a key is pressed.

```js
document.addEventListener("keydown", handleKeyDown);
```

`keyup` occurs when the key is released.

```js
document.addEventListener("keyup", handleKeyUp);
```

For many command and shortcut scenarios, `keydown` is the more useful event.

---

# 35. `event.code` vs `event.key`

Keyboard events provide both.

Example:

```js
document.addEventListener("keydown", (event) => {
  console.log(event.key);
  console.log(event.code);
});
```

For a physical keyboard key, these values represent different concepts.

```text
event.key
↓
Meaning/value of the key

event.code
↓
Physical key position identifier
```

For example, a key may have:

```text
key  = "a"
code = "KeyA"
```

Keyboard layout can affect `event.key`.

---

# 36. Keyboard Modifiers

Keyboard events expose modifier information.

Example:

```js
document.addEventListener("keydown", (event) => {
  if (event.ctrlKey && event.key === "s") {
    event.preventDefault();

    console.log("Save shortcut.");
  }
});
```

Other modifier properties include:

```js
event.shiftKey
event.altKey
event.metaKey
event.ctrlKey
```

These are useful for keyboard shortcuts.

---

# 37. Be Careful with Keyboard Shortcuts

Global shortcuts can interfere with:

* browser behavior
* operating-system shortcuts
* assistive technologies
* text editing
* application inputs

Only override browser defaults when the interaction is meaningful and expected.

---

# 38. Input Events

For text input, the `input` event is often more useful than `change`.

Example:

```js
const input = document.querySelector("#search");

input.addEventListener("input", (event) => {
  console.log(event.target.value);
});
```

It responds as the value changes.

---

# 39. `change` Event

The `change` event generally represents a committed value change.

For text inputs, its behavior differs from `input`.

Example:

```js
input.addEventListener("change", (event) => {
  console.log(event.target.value);
});
```

Use the event that matches the desired interaction semantics.

---

# 40. Focus Events

Common focus-related events:

```text
focus
blur
focusin
focusout
```

Example:

```js
input.addEventListener("focus", () => {
  console.log("Input focused.");
});

input.addEventListener("blur", () => {
  console.log("Input lost focus.");
});
```

Focus management is important for:

* forms
* accessibility
* keyboard navigation
* dialogs
* validation

---

# 41. `focusin` and `focusout`

Unlike `focus` and `blur`, `focusin` and `focusout` participate in event bubbling.

This can make them useful for delegated focus handling.

Example:

```js
form.addEventListener("focusin", (event) => {
  console.log("Focus entered:", event.target);
});
```

This can be useful when managing many form controls from one parent.

---

# 42. Form Events

Important form events include:

```text
submit
reset
input
change
invalid
```

Example:

```js
form.addEventListener("submit", (event) => {
  event.preventDefault();

  console.log("Form submitted.");
});
```

Form events are essential in interactive applications.

---

# 43. The `submit` Event

The `submit` event belongs to the form.

Do not rely only on the submit button's `click` event.

Use:

```js
form.addEventListener("submit", handleSubmit);
```

because forms can also be submitted through keyboard interactions.

This is especially important for accessibility.

---

# 44. Scroll Events

The browser can dispatch `scroll`.

Example:

```js
window.addEventListener("scroll", () => {
  console.log(window.scrollY);
});
```

Scroll events can occur very frequently.

Avoid expensive work directly inside the handler.

---

# 45. Throttling Scroll Work

A naive implementation:

```js
window.addEventListener("scroll", () => {
  performExpensiveWork();
});
```

may run too frequently.

Possible strategies include:

* throttling
* `requestAnimationFrame()`
* `IntersectionObserver`
* avoiding unnecessary DOM reads/writes

Example:

```js
let scheduled = false;

window.addEventListener("scroll", () => {
  if (scheduled) {
    return;
  }

  scheduled = true;

  requestAnimationFrame(() => {
    scheduled = false;

    performExpensiveWork();
  });
});
```

This coordinates work with the browser's rendering cycle.

---

# 46. Resize Events

The `resize` event is associated with the browser window.

Example:

```js
window.addEventListener("resize", () => {
  console.log(window.innerWidth);
});
```

Like `scroll`, resize can occur frequently.

Avoid expensive calculations on every event without a reason.

For element-size observation, `ResizeObserver` is often more appropriate than listening to window resize.

---

# 47. Load Events

The `load` event indicates that a resource or document has finished loading according to the relevant target.

Example:

```js
window.addEventListener("load", () => {
  console.log("Page load event fired.");
});
```

`load` is broader than simply waiting for the HTML parser to finish.

---

# 48. `DOMContentLoaded`

`DOMContentLoaded` fires when the document has been parsed and the DOM is ready.

Example:

```js
document.addEventListener(
  "DOMContentLoaded",
  () => {
    console.log("DOM ready.");
  }
);
```

This is different from `load`.

Conceptually:

```text
DOMContentLoaded
↓
HTML parsed and DOM constructed

load
↓
Document and required subresources finished loading
```

---

# 49. `load` vs `DOMContentLoaded`

| Event              | General Meaning                                                                              |
| ------------------ | -------------------------------------------------------------------------------------------- |
| `DOMContentLoaded` | HTML document has been parsed                                                                |
| `load`             | The window/document loading process has completed according to the event's loading semantics |

For DOM-only initialization, `DOMContentLoaded` may be enough.

For logic that depends on loaded resources, `load` may be more appropriate.

---

# 50. Page Lifecycle Events

Browsers expose several lifecycle-related events.

Examples include:

```text
DOMContentLoaded
load
beforeunload
unload
pageshow
pagehide
visibilitychange
```

Some of these have important restrictions and performance implications.

Modern applications should prefer lifecycle APIs that accurately represent the behavior they need rather than automatically relying on `unload`.

---

# 51. `visibilitychange`

The `visibilitychange` event fires when the document's visibility state changes.

Example:

```js
document.addEventListener(
  "visibilitychange",
  () => {
    if (document.hidden) {
      console.log("Page hidden.");
    } else {
      console.log("Page visible.");
    }
  }
);
```

This is useful for:

* pausing unnecessary work
* reducing polling
* saving battery
* refreshing stale data
* media control

---

# 52. `document.hidden`

Inside the visibility handler:

```js
document.hidden
```

returns:

```js
true
```

when the document is hidden, or:

```js
false
```

when visible.

Example:

```js
console.log(document.hidden);
```

The value is not the same thing as browser online/offline state.

---

# 53. `pageshow`

`pageshow` is useful when a document becomes visible as a page in the browser's session history.

Example:

```js
window.addEventListener("pageshow", () => {
  console.log("Page shown.");
});
```

It can be especially relevant when navigating backward or forward.

---

# 54. `pagehide`

`pagehide` is related to the page being hidden as part of navigation or browser lifecycle behavior.

Example:

```js
window.addEventListener("pagehide", () => {
  console.log("Page hidden.");
});
```

For lifecycle-sensitive applications, `pagehide` can be more useful than relying on `unload`.

---

# 55. Avoid Depending on `unload`

The `unload` event has important reliability and performance limitations.

Modern applications should generally prefer more appropriate lifecycle signals such as:

```text
visibilitychange
pagehide
```

depending on the problem being solved.

Do not treat `unload` as a guaranteed place for important data persistence or network requests.

---

# 56. `beforeunload`

`beforeunload` can be used when the user may have unsaved changes.

Example:

```js
window.addEventListener("beforeunload", (event) => {
  event.preventDefault();
});
```

Browsers control the exact confirmation UI.

Use this feature carefully and only when there is a genuine risk of data loss.

---

# 57. Do Not Abuse `beforeunload`

It should not be used to trap users on a page.

Use it only when necessary, such as when meaningful unsaved data could be lost.

For many applications, saving state continuously is better than relying on a last-minute leave warning.

---

# 58. `hashchange`

The `hashchange` event fires when the URL fragment changes.

Example:

```js
window.addEventListener("hashchange", () => {
  console.log("Hash changed.");
});
```

If the URL changes from:

```text
#about
```

to:

```text
#projects
```

the event can fire.

This is useful for simple fragment-based navigation.

---

# 59. `popstate`

The History API can dispatch `popstate` when the active history entry changes in relevant circumstances.

Example:

```js
window.addEventListener("popstate", () => {
  console.log("History state changed.");
});
```

This is important for SPA routing and browser back/forward interactions.

---

# 60. `storage`

The `storage` event can notify a different document in the same origin when Web Storage changes.

Example:

```js
window.addEventListener("storage", (event) => {
  console.log(event.key);
  console.log(event.newValue);
});
```

A crucial detail:

> The document that performs the storage change does not receive the `storage` event for that same change.

The event is intended for communication with other relevant documents.

---

# 61. `online` and `offline`

The browser can report network-state transitions:

```js
window.addEventListener("online", () => {
  console.log("Online state.");
});

window.addEventListener("offline", () => {
  console.log("Offline state.");
});
```

Remember:

```text
online
≠
guaranteed internet access
```

These events provide a browser-level network state signal.

---

# 62. `error` Event

The browser can dispatch error events for certain failures.

For example:

```js
window.addEventListener("error", (event) => {
  console.error("Browser error:", event.message);
});
```

Error event behavior differs depending on the source.

For example:

* JavaScript execution errors
* resource loading errors
* element-level failures

may expose different information.

---

# 63. `unhandledrejection`

Unhandled Promise rejections can be observed through:

```js
window.addEventListener(
  "unhandledrejection",
  (event) => {
    console.error(
      "Unhandled rejection:",
      event.reason
    );
  }
);
```

This can be useful for diagnostics.

However, global error handling should complement—not replace—local error handling.

---

# 64. Global Error Handling

A global handler can help detect unexpected failures:

```js
window.addEventListener("error", handleError);
window.addEventListener(
  "unhandledrejection",
  handleRejection
);
```

But production applications should still handle expected failures at the point where they occur.

For example:

```js
try {
  await saveData();
} catch (error) {
  showError(error);
}
```

is better than allowing every expected failure to reach a global handler.

---

# 65. Event Listeners and Exceptions

If one listener throws an exception, it does not automatically mean the entire event system stops functioning permanently.

However, throwing errors from event handlers without proper handling can make application behavior difficult to debug.

Keep event handlers focused and handle expected failure cases explicitly.

---

# 66. Custom Events

```js
const event = new CustomEvent("profileUpdated", {
```

This allows application-specific event communication.

```js
const event = new CustomEvent("projectCreated", {
```

```js
window.addEventListener(
```

# 68. Dispatching Events

To manually trigger an event:

```js
const event = new Event("refresh");

window.dispatchEvent(event);
```

Listener:

```js
window.addEventListener("refresh", () => {
  console.log("Refresh event received.");
});
```

This creates an event-driven communication mechanism.

Use it when it genuinely fits the architecture.

---

# 69. Custom Events vs React State

In React applications, custom DOM events are often less necessary because React already provides:

* props
* state
* Context
* callbacks
* event handlers

For example, instead of:

```js
window.dispatchEvent(...)
```

a React application may simply update shared state or call a callback.

Custom browser events are more useful when integrating:

* non-React code
* browser-level systems
* independent web components
* third-party widgets

---

# 70. Event Delegation

Event delegation means putting one listener on a parent instead of many listeners on individual children.

Example:

```html
<ul id="projects">
  <li>React</li>
  <li>Next.js</li>
  <li>JavaScript</li>
</ul>
```

Instead of:

```js
document
  .querySelectorAll("#projects li")
  .forEach((item) => {
    item.addEventListener("click", handleClick);
  });
```

use:

```js
const list = document.querySelector("#projects");

list.addEventListener("click", (event) => {
  const item = event.target.closest("li");

  if (!item) {
    return;
  }

  console.log(item.textContent);
});
```

This relies on bubbling.

---

# 71. Why Event Delegation Helps

It can reduce:

* number of listeners
* setup work
* cleanup complexity

It can also work well with dynamically added elements.

However, the listener must correctly identify the intended event target.

---

# 72. Event Delegation and `closest()`

A common pattern:

```js
const container = document.querySelector(
  "#container"
);

container.addEventListener("click", (event) => {
  const button = event.target.closest(
    "[data-action]"
  );

  if (!button) {
    return;
  }

  console.log(
    button.dataset.action
  );
});
```

This is especially useful for dynamic interfaces.

---

# 73. Browser Events and Dynamic DOM

Suppose:

```js
container.innerHTML += `
  <button data-action="save">
    Save
  </button>
`;
```

An event listener attached directly to a previous button does not automatically attach to the new button.

Event delegation can solve this:

```js
container.addEventListener("click", handleClick);
```

Now newly added matching elements can participate in the same delegated handler.

---

# 74. Event Listener Performance

Most event listeners are inexpensive.

The performance problem usually comes from:

* excessive listener count
* expensive handler logic
* forced synchronous layout
* unnecessary DOM operations
* high-frequency events

Events such as:

```text
scroll
mousemove
pointermove
resize
touchmove
```

can happen frequently.

Optimize the handler, not merely the event registration.

---

# 75. Event Handler Work

Avoid:

```js
window.addEventListener("scroll", () => {
  performHugeCalculation();
  updateManyElements();
  readAndWriteLayoutRepeatedly();
});
```

Prefer:

```text
Event
 ↓
Minimal work
 ↓
Schedule necessary updates
 ↓
Batch DOM operations
```

For visual updates, `requestAnimationFrame()` can help.

---

# 76. Events and Layout Thrashing

A problematic handler may repeatedly alternate between DOM reads and writes:

```js
element.style.width = `${element.offsetWidth + 1}px`;
```

Repeated layout reads and writes can cause unnecessary browser work.

When building high-performance interactions, understand:

* layout
* style calculation
* painting
* compositing

Event frequency and rendering behavior should be considered together.

---

# 77. Event Listener `passive` and Scrolling

Touch and wheel-related handlers can affect scrolling performance when the browser must wait to know whether the event will be cancelled.

A passive listener communicates:

```js
{
  passive: true
}
```

meaning:

> This handler will not call `preventDefault()`.

This can help scrolling performance in appropriate scenarios.

---

# 78. Event Order Matters

Different browser interactions generate sequences of events.

For example, a button interaction may involve:

```text
pointerdown
pointerup
click
```

Keyboard interaction can involve:

```text
keydown
keyup
```

A form interaction may produce:

```text
input
change
submit
```

Do not assume every interaction maps to one event.

Choose the event whose semantics match the behavior you want.

---

# 79. Prefer Semantic Events

If you want to know when a form is submitted, use:

```js
form.addEventListener("submit", handleSubmit);
```

rather than trying to infer it from:

```js
button.addEventListener("click", handleClick);
```

The semantic event captures more ways the action can occur.

This improves robustness and accessibility.

---

# 80. Browser Events and Accessibility

Keyboard and assistive technology users may interact differently from mouse users.

Avoid implementing important functionality exclusively through:

```text
mouseover
mousedown
mousemove
```

Prefer semantic HTML and appropriate events.

For example:

```html
<button>
  Save
</button>
```

automatically supports important keyboard interaction patterns.

This is generally better than:

```html
<div onclick="...">
  Save
</div>
```

---

# 81. Do Not Replace Native Controls Unnecessarily

A native:

```html
<button>
```

already provides:

* keyboard behavior
* focus behavior
* semantics
* accessibility expectations

A clickable `div` requires you to recreate much of that behavior.

Browser events should enhance semantic HTML rather than replace it without a reason.

---

# 82. Event Listeners and `this`

Regular functions and arrow functions behave differently with `this`.

Example:

```js
button.addEventListener("click", function () {
  console.log(this);
});
```

In this style, `this` can refer to the current event listener's target in the browser's event listener callback semantics.

With an arrow function:

```js
button.addEventListener("click", () => {
  console.log(this);
});
```

the arrow function does not create its own `this`.

The exact surrounding context therefore matters.

In modern code, `event.currentTarget` is often clearer when you explicitly need the listener target.

---

# 83. Prefer `event.currentTarget` When Appropriate

Instead of relying on:

```js
this
```

you can write:

```js
button.addEventListener("click", (event) => {
  console.log(event.currentTarget);
});
```

This communicates exactly what you want:

> the element whose listener is currently executing.

This is particularly useful with arrow functions.

---

# 84. Event Listener Identity

To remove a listener, the browser needs the same listener identity.

Correct:

```js
function handleClick() {
  console.log("Clicked");
}

button.addEventListener("click", handleClick);
button.removeEventListener("click", handleClick);
```

Incorrect:

```js
button.addEventListener("click", () => {
  console.log("Clicked");
});

button.removeEventListener("click", () => {
  console.log("Clicked");
});
```

These are two different function objects.

# 85. React and Browser Events

React provides its own event handling system at the component level.

Typical React code:

```jsx
function SaveButton() {
  function handleClick() {
    console.log("Saved.");
  }

  return (
    <button onClick={handleClick}>
      Save
    </button>
  );
}
```

This is different from manually calling:

```js
button.addEventListener("click", handleClick);
```

inside the component.

---

# 86. React Event Handlers vs Native Event Listeners

React:

```jsx
<button onClick={handleClick}>
  Save
</button>
```

Native DOM:

```js
button.addEventListener(
  "click",
  handleClick
);
```

In normal React components, prefer React's event model for events on rendered React elements.

Use native listeners when interacting with:

* `window`
* `document`
* external browser APIs
* non-React DOM
* third-party libraries

---

# 87. React and `window` Events

Example:

```jsx
useEffect(() => {
  function handleResize() {
    console.log(window.innerWidth);
  }

  window.addEventListener(
    "resize",
    handleResize
  );

  return () => {
    window.removeEventListener(
      "resize",
      handleResize
    );
  };
}, []);
```

This is an appropriate use of a native event listener inside React.

The component subscribes to an external browser system and cleans up the subscription.

---

# 88. React Cleanup Pattern

The general pattern is:

```jsx
useEffect(() => {
  const handler = () => {
    // Handle event
  };

  target.addEventListener(
    "event",
    handler
  );

  return () => {
    target.removeEventListener(
      "event",
      handler
    );
  };
}, []);
```

This is one of the most important `useEffect` patterns to understand.

---

# 89. React State and Event Listeners

Be careful when event listeners capture React state.

Example:

```jsx
useEffect(() => {
  function handleKeyDown() {
    console.log(count);
  }

  window.addEventListener(
    "keydown",
    handleKeyDown
  );

  return () => {
    window.removeEventListener(
      "keydown",
      handleKeyDown
    );
  };
}, []);
```

Because the effect has an empty dependency array, the handler can retain the state value from the render in which the effect was created.

This is a common source of stale closures.

---

# 90. Functional State Updates

When an event handler needs to update state based on the previous value, a functional update can be safer:

```jsx
setCount((currentCount) => {
  return currentCount + 1;
});
```

This avoids depending on an outdated captured state value for the calculation.

This concept is especially useful for:

* keyboard listeners
* intervals
* timers
* subscriptions
* external event sources

---

# 91. `useEffect` Is About Synchronization

A useful mental model is:

```text
React component
      ↓
Subscribes to browser event
      ↓
Browser changes
      ↓
Event fires
      ↓
Handler updates React state
      ↓
React re-renders
```

This is exactly the kind of external synchronization `useEffect` is commonly used for.

---

# 92. React Strict Mode and Event Listeners

Development configurations may intentionally exercise effect setup and cleanup more than once to reveal lifecycle problems.

Correct code:

```jsx
useEffect(() => {
  window.addEventListener("resize", handleResize);

  return () => {
    window.removeEventListener("resize", handleResize);
  };
}, []);
```

will remain safe because every setup has matching cleanup.

If duplicate listeners appear during development, inspect cleanup before blaming React.

# 93. Next.js Browser Events

In Next.js, browser event APIs require a browser environment.

For example:

```jsx
"use client";

import { useEffect } from "react";

export default function Component() {
  useEffect(() => {
    function handleResize() {
      console.log(window.innerWidth);
    }

    window.addEventListener(
      "resize",
      handleResize
    );

    return () => {
      window.removeEventListener(
        "resize",
        handleResize
      );
    };
  }, []);

  return <p>Resize the browser.</p>;
}
```

The `"use client"` directive establishes the client component boundary.

The important principle is:

```text
window/document/browser event
        ↓
client-side code
```

# 94. Browser Events and Server Rendering

Code such as:

```js
window.addEventListener(...)
```

cannot execute in a server environment where `window` does not exist.

Therefore, keep browser-specific event logic on the client.

This is one reason understanding the browser environment is important before working deeply with Next.js.

# 95. Common Mistake: Using `onclick`

You may see:

```js
button.onclick = handleClick;
```

This works, but `addEventListener()` is generally more flexible.

For example:

```js
button.addEventListener(
  "click",
  handleClick
);
```

allows multiple independent listeners.

With:

```js
button.onclick = handleClick;
```

assigning another handler replaces the previous `onclick` assignment.

For modern code, `addEventListener()` is generally the preferred event subscription API.

---

# 96. Common Mistake: Calling the Handler Immediately

Incorrect:

```js
button.addEventListener(
  "click",
  handleClick()
);
```

This invokes the function immediately.

Correct:

```js
button.addEventListener(
  "click",
  handleClick
);
```

The browser needs the function itself so it can call it later.

---

# 97. Common Mistake: Using `event.target` Carelessly

Consider:

```html
<button>
  <span>Save</span>
</button>
```

A click on the text may make:

```js
event.target
```

the `<span>`.

If you need the button that owns the listener, use:

```js
event.currentTarget
```

or appropriate delegation logic.

---

# 98. Common Mistake: Calling `preventDefault()` Without a Reason

Avoid:

```js
event.preventDefault();
```

everywhere.

Preventing default behavior can break:

* links
* forms
* keyboard interaction
* scrolling
* browser accessibility behavior

Only prevent the default action when your application intentionally replaces it.

---

# 99. Common Mistake: Overusing `stopPropagation()`

This can hide event-flow problems rather than solving them.

Before using:

```js
event.stopPropagation();
```

understand:

* who needs the event
* why the parent should not receive it
* whether event delegation depends on bubbling

Treat propagation as part of the architecture.

---

# 100. Common Mistake: Heavy Work on High-Frequency Events

Avoid performing expensive work directly in:

```js
mousemove
scroll
pointermove
resize
touchmove
```

without considering performance.

Use:

* throttling
* debouncing
* `requestAnimationFrame()`
* observers
* event delegation

where appropriate.

---

# 101. Common Mistake: Forgetting Cleanup

Incorrect:

```jsx
useEffect(() => {
  window.addEventListener(
    "resize",
    handleResize
  );
}, []);
```

Better:

```jsx
useEffect(() => {
  window.addEventListener(
    "resize",
    handleResize
  );

  return () => {
    window.removeEventListener(
      "resize",
      handleResize
    );
  };
}, []);
```

---

# 102. Common Mistake: Using Events Instead of Observers

Some browser behaviors have dedicated observer APIs.

Instead of continuously listening to:

```text
scroll
resize
```

and calculating everything manually, consider:

```text
IntersectionObserver
ResizeObserver
MutationObserver
PerformanceObserver
```

These APIs are often more appropriate for their specific problems.

Events are not always the best abstraction.

---

# 103. Events vs Observers

| Problem                 | Common Tool            |
| ----------------------- | ---------------------- |
| User clicks             | Event                  |
| Keyboard interaction    | Event                  |
| Window resize           | `resize` event         |
| Element size changes    | `ResizeObserver`       |
| Element enters viewport | `IntersectionObserver` |
| DOM tree changes        | `MutationObserver`     |
| Performance timeline    | `PerformanceObserver`  |

Use the API that matches the information you need.

# 104. Event Delegation vs Individual Listeners

Use individual listeners when:

```text
Few stable elements
```

Use delegation when:

```text
Many similar descendants
Dynamic descendants
Shared parent behavior
```

Example:

```js
list.addEventListener("click", handleListClick);
```

can be more maintainable than hundreds of individual click listeners.

However, delegation is not automatically better. Choose according to the UI structure.

---

# 105. Event Ordering and Asynchronous Code

Suppose:

```js
button.addEventListener("click", async () => {
  console.log("Start");

  await saveData();

  console.log("Finished");
});
```

The event handler starts synchronously.

Once it reaches:

```js
await saveData();
```

the handler yields while the asynchronous operation continues.

This connects browser events to the broader JavaScript asynchronous model.

---

# 106. Events and Timers

Timers can be started from event handlers:

```js
button.addEventListener("click", () => {
  setTimeout(() => {
    console.log("Delayed action.");
  }, 1000);
});
```

This combines:

```text
Browser event
+
timer
+
event loop
```

Understanding all three concepts is important for frontend development.

---

# 107. Events and Promises

An event handler can also perform asynchronous operations:

```js
button.addEventListener("click", async () => {
  try {
    const response = await fetch("/api/save");

    if (!response.ok) {
      throw new Error("Save failed.");
    }

    console.log("Saved.");
  } catch (error) {
    console.error(error);
  }
});
```

This is a very common real-world pattern.

---

# 108. Events and AbortController

`AbortController` can be used to cancel certain asynchronous browser operations.

Example:

```js
const controller = new AbortController();

fetch("/api/data", {
  signal: controller.signal,
});
```

Later:

```js
controller.abort();
```

The same `AbortController` concept can also coordinate event listener cleanup through the `signal` option.

This provides a unified cancellation model for some browser APIs.

# 109. Security Considerations

Events themselves are not a security boundary.

Do not assume:

```js
button.addEventListener("click", () => {
  // trusted operation
});
```

means the operation is secure.

A user can modify browser-side code and requests.

Security-sensitive actions must be validated and authorized on the server.

---

# 110. Event Handlers and Untrusted Input

Events can contain user-controlled data.

For example:

```js
input.addEventListener("input", (event) => {
  const value = event.target.value;
});
```

That value is untrusted input.

Do not insert it into HTML using unsafe methods such as:

```js
element.innerHTML = value;
```

without understanding the security implications.

Prefer:

```js
element.textContent = value;
```

when displaying plain text.

and then manually trying to recreate:

# 112. Event Listeners and Memory

A listener can keep references alive through closures.

Example:

```js

  return () => {
    console.log(largeObject);
```

If the listener remains attached:


# 124. Browser Events and the Event Loop

Browser events are integrated with the broader JavaScript execution model.

Conceptually:

```text
Browser activity
      ↓
Event becomes ready
      ↓
Event callback scheduled
      ↓
JavaScript executes handler
      ↓
Handler may schedule more work
      ↓
Browser continues processing
```

The exact scheduling details depend on the event, browser, rendering cycle, and other queued work.

The key principle is that browser events do not bypass JavaScript's single-threaded execution model on the main thread.

---

# 125. Events Do Not Interrupt Running JavaScript

Suppose:

```js
button.addEventListener("click", handleClick);

const start = Date.now();

while (Date.now() - start < 3000) {
  // Blocking work
}
```

A click that happens during the blocking loop cannot cause JavaScript to interrupt that loop and run `handleClick()` in the middle of it.

The handler must wait until the current synchronous JavaScript task finishes.

This is a fundamental reason why long-running JavaScript makes interfaces unresponsive.

can generate frequent updates.


to align work with browser rendering.

Do not assume every event should directly manipulate the DOM.

# 133. Best Practices

### Prefer `addEventListener()`

Use:

```js
addEventListener()
```

instead of relying on `onclick` and similar property assignment for most modern event handling.

### Keep handlers focused

An event handler should perform a clear piece of work.

### Clean up listeners

Especially in React effects and long-lived applications.

### Understand propagation

Know the difference between:

```js
target
currentTarget
```

and understand bubbling before using:

```js
stopPropagation()
```

### Avoid unnecessary `preventDefault()`

Only cancel browser behavior when you intentionally replace it.

### Use semantic HTML

Prefer native controls such as:

```html
button
form
input
a
```

over recreating their behavior with generic elements.

### Optimize high-frequency events

Consider:

```text
throttle
debounce
requestAnimationFrame
observers
```

### Use the right API

Do not force an event into a problem better solved by an observer.

### Treat event data as untrusted input

Validate and safely render user-controlled values.

### Separate UI events from security

Client-side events are not security boundaries.

# 134. Final Mental Model

The browser is continuously observing many types of activity:

```text
User
 ↓
click
keydown
input
focus

Browser
 ↓
resize
scroll
visibilitychange
online
offline

Document
 ↓
DOMContentLoaded
page lifecycle

Application
 ↓
CustomEvent
```

JavaScript subscribes to this activity:

```text
Event source
    ↓
addEventListener()
    ↓
Event object
    ↓
Handler
    ↓
Application logic
```

The most important concepts to remember are:

> `addEventListener()` subscribes to browser activity.

> The event object contains information about what happened.

> `event.target` identifies where the event originated.

> `event.currentTarget` identifies the object whose listener is currently executing.

> `preventDefault()` cancels the browser's default action.

> `stopPropagation()` affects event propagation.

> Bubbling enables powerful patterns such as event delegation.

> High-frequency events require careful performance handling.

> In React, native browser listeners should usually be synchronized through `useEffect` and cleaned up properly.

> In Next.js, browser event APIs belong to client-side execution.

Once these concepts are understood, DOM interactions, React event handling, routing events, browser lifecycle behavior, and many frontend performance patterns become much easier to reason about.
